# Clientes tipados

DaloyJS incluye **dos** formas de llamar a tu API con seguridad de tipos completa. Usa la que mejor se adapte a tu consumidor.

## 1. Cliente tipado en proceso (sin generación de código) [#1-in-process-typed-client-zero-codegen]

Para consumidores de TypeScript dentro del mismo monorepo (pruebas, herramientas internas, server actions de Next.js):

```ts
import { createInProcessClient } from "@daloyjs/core/client";
import { app } from "./app.js";

const client = createInProcessClient(app);

const r = await client.getBookById({ params: { id: "1" } });
//    ^? { status: 200; body: { id: string; title: string } }
//      | { status: 404; body: ProblemJson }

if (r.status === 200) {
  console.log(r.body.title); // string, totalmente tipado
}
```

El cliente se indexa por `operationId`, devuelve una unión discriminada de `{status, body, headers}` e infiere todo a partir de la propia definición de la ruta. No requiere ningún paso de compilación.

### Parámetros de ruta [#path-parameters]

Los parámetros de ruta se sustituyen por segmento completo, así que `:id` nunca coincide dentro de `:idx`, y cada valor se codifica en porcentaje dentro de su propio segmento. Desde la versión 1.3.7, un método generado lanza un `TypeError` antes de enviar ninguna petición cuando falta un parámetro, está vacío o es `.` o `..`. El análisis de URL resolvería un segmento de punto (incluso escrito como `%2E%2E`) y redirigiría la llamada en silencio; por ejemplo, convertiría `DELETE /orgs/:org/members/..` en `DELETE /orgs/:org`. Las rutas con comodín (`*path`, o un `*` sin nombre llamado `wildcard`) aceptan un valor separado por `/`; cada segmento se codifica y se comprueba de la misma forma.

```ts
// app.get("/files/*path", { operationId: "getFile", ... })
await client.getFile({ params: { path: "docs/guide.md" } }); // GET /files/docs/guide.md

await client.getBookById({ params: { id: ".." } });
// TypeError: Invalid path parameter "id" for /books/:id: empty and "."/".." segments are not allowed
```

<Callout type="tip" title="Compón tuplas de rutas en lugar de ampliar la App.">
<p>Exporta los archivos de rutas con <code>defineRoute()</code> y registra una tupla literal con <code>app.registerRoutes(\[...\])</code>{". "}Las llamadas encadenadas a <code>route()</code> también funcionan. Hay dos cosas que borran la inferencia de forma deliberada y reducen el cliente a una superficie poco precisa:</p>
<ul>
<li>Anotar la instancia con un simple <code>const app: App = ...</code> (o devolver <code>: App</code>{" "}desde una fábrica). La anotación que amplía el tipo descarta las rutas acumuladas, así que deja que el tipo se infiera.</li>
<li>Registrar las rutas como sentencias separadas sobre una variable declarada antes, en lugar de devolver el resultado encadenado o usar <code>registerRoutes()</code>.</li>
</ul>
<p>La guía del monolito modular muestra una composición en varios archivos con tuplas de rutas de varios contextos delimitados. Los <code>group()</code> con callback y el <code>register()</code> de los plugins siguen aportando un encapsulamiento en tiempo de ejecución, pero sus callbacks no pueden ampliar el genérico de TypeScript de la variable padre. Usa las tuplas de rutas como el límite de composición del cliente tipado.</p>
</Callout>

## 2. SDK de Hey API (entre lenguajes, entre repositorios, en tiempo de build) [#2-hey-api-sdk-cross-language-cross-repo-build-time]

Para consumidores fuera del monorepo o que usen otros lenguajes, genera un SDK de fetch totalmente tipado con [@hey-api/openapi-ts](https://heyapi.dev/openapi-ts/get-started).

```bash
pnpm add -D @hey-api/openapi-ts@0.0.0-next-20260930190945 prettier
```

```ts
// openapi-ts.config.ts
import { defineConfig } from "@hey-api/openapi-ts";

export default defineConfig({
  input: "./generated/openapi.json",
  output: { path: "./generated/client", postProcess: ["prettier"] },
  plugins: ["@hey-api/client-fetch", "@hey-api/typescript", "@hey-api/sdk"],
});
```

```json
// package.json
"scripts": {
  "gen:openapi": "node scripts/dump-openapi.ts",
  "gen:client":  "openapi-ts",
  "gen":         "pnpm gen:openapi && pnpm gen:client"
}
```

```bash
pnpm gen
# escribe:
#   generated/openapi.json
#   generated/client/{client.gen.ts, sdk.gen.ts, types.gen.ts, index.ts}
```

## Usar el SDK generado [#using-the-generated-sdk]

```ts
import { client } from "./generated/client/client.gen.js";
import { getBookById } from "./generated/client/sdk.gen.js";

client.setConfig({ baseUrl: "https://api.example.com" });

const { data, error } = await getBookById({ path: { id: "1" } });
if (error) console.error(error);
else if (data) console.log(data.title);
```

## ¿Cuál debo usar? [#which-one-should-i-use]

| Caso de uso | Opción |
| --- | --- |
| Consumidor TypeScript del mismo repositorio (pruebas, herramientas internas) | `createInProcessClient` |
| Aplicación web o bundle de React Native móvil en un repositorio separado | SDK de Hey API |
| Consumidor que no usa TypeScript (Python, Swift, Kotlin) | Documento OpenAPI + el generador que prefiera |
| SDK público para terceros | SDK de Hey API, publicado como su propio paquete |

## ¿Vienes de ts-rest? [#coming-from-ts-rest]

[ts-rest](https://ts-rest.com/) es una biblioteca popular basada en contratos que ofrece tipos TypeScript de extremo a extremo **sin generación de código**, al compartir un contrato (`initContract`) entre un servidor basado en adaptadores (Express, Fastify, NestJS, Next.js) y un cliente de fetch (`initClient`). Si te gusta ese modelo, DaloyJS te resultará familiar, con dos diferencias.

En primer lugar, en DaloyJS **la definición de la ruta es el contrato**: no hay ningún objeto de contrato separado que mantener sincronizado. El `createClient` en proceso que se muestra arriba ofrece la misma experiencia sin generación de código y con tipos compartidos para los consumidores TypeScript del mismo repositorio.

En segundo lugar, la seguridad de tipos de ts-rest es exclusiva de TypeScript y exige que el cliente importe el contrato. DaloyJS genera a partir de las mismas rutas una especificación **OpenAPI 3.1** de primera clase y un SDK de Hey API, así que también cubre a los consumidores que no pueden importar tus tipos (otros repositorios, otros lenguajes, SDK públicos). En ts-rest, OpenAPI es un complemento opcional (`@ts-rest/open-api`). DaloyJS es además el propio servidor y runtime, portable entre Node, Bun, Deno, Cloudflare y Vercel, en lugar de una capa de tipos montada sobre un framework independiente.

|  | ts-rest | DaloyJS |
| --- | --- | --- |
| Origen del contrato | Objeto `initContract` separado | La propia definición de la ruta |
| Cliente tipado sin generación de código | Sí (`initClient`, solo TypeScript) | Sí (`createClient`, solo TypeScript) |
| Clientes entre lenguajes y entre repositorios | Complemento de OpenAPI (`@ts-rest/open-api`) | OpenAPI 3.1 + SDK de Hey API, de primera clase |
| Servidor | Adaptador sobre Express / Fastify / NestJS / Next.js | Integrado, portable entre runtimes |
| Validación en tiempo de ejecución | Standard Schema (Zod / Valibot / ArkType) | Standard Schema (Zod / Valibot / ArkType / TypeBox) |
| Valores de seguridad por defecto | Lo implementas tú | Cabeceras y límites de cuerpo activados por defecto; CSRF y límites de frecuencia a una línea de distancia |

¿Necesitas un contrato más grande para validar la salida de tu generador? Usa la [demo de API REST falsa a gran escala](/docs/tutorials/fake-rest-api) (en inglés) como caso de estrés, en lugar de una aplicación de tutorial mínima.
