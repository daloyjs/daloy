### `RateLimitOptions` [#rate-limit-options]

A limiter placed before `preBody` auth also counts requests that auth rejects by throwing, so failed credential guesses consume the budget.

By default the limiter sends `X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `X-RateLimit-Reset`. Set `standardHeaders: "draft-8"` to also send the IETF `RateLimit` and `RateLimit-Policy` headers. Add `legacyHeaders: false` to send only the IETF pair. The option names and the policy name match express-rate-limit, so clients written against an Express API keep working after a move to Daloy.

```ts
app.use(rateLimit({ windowMs: 60_000, max: 120, standardHeaders: "draft-8", legacyHeaders: false }));
// RateLimit-Policy: "120-in-60sec"; q=120; w=60
// RateLimit: "120-in-60sec"; r=119; t=60
```

`t` is the number of seconds until the window resets. No partition key (`pk`) is sent, so the bucket key never leaves the server. Turning headers off never turns enforcement off. Browsers can only read these headers cross-origin when they are listed in `cors({ exposedHeaders })`.

### `requireScopes()` options [#require-scopes-options]

`requireScopes()` reads `ctx.state.user.scopes`, which `jwk()`, `bearerAuth()` and other auth helpers fill in. `jwk()` builds that list from the token's `scope` claim (space-delimited string), or, when `scope` is absent, from `scp` (a space-delimited string as Microsoft Entra ID issues it since 1.10.0, or an array) or `scopes` (array). Only an **own** `scopes` property counts (since 1.16.0, matching `requireRoles()`): an inherited one, such as a polluted `Object.prototype` or a class getter, grants nothing, so return a plain object from a custom `bearerAuth({ validate })`. A caller without credentials gets `401` with a `WWW-Authenticate: Bearer scope="..."` challenge; a caller with too few scopes gets `403`.

By default the check runs in `beforeHandle`, after the request body is read and validated. That means a valid token with too few scopes and a malformed body gets `400`, and the server parses a body from a caller it is about to refuse. Since 1.10.0 you can authorize in `preBody` instead, right after header-only authentication:

```ts
import { App, every, jwk, requireScopes } from "@daloyjs/core";

app.use(every(
  jwk({ jwks, algorithms: ["RS256"], issuer, audience, maxLifetimeSeconds: 86_400 }),
  // 403 before any body I/O; owning either scope is enough.
  requireScopes(["agent.chat", "agent.admin"], { phase: "preBody", match: "any" }),
));
```

- `phase: "preBody"` runs the same check before the body is read: missing credentials are `401`, insufficient scope is `403`, whatever the body contains. The authentication hook must run first (earlier in `every()`, or registered earlier with `app.use()`), or every request is a `401`.
- `match: "any"` accepts a caller that owns at least one listed scope. It **requires** `phase: "preBody"`, and construction throws otherwise. Stored-response replays (`idempotency()`, `responseCache()`) run in `beforeHandle` and only understand all-of requirements, so an any-of check must reject before they can serve a stored response. All-of guards keep feeding those replay checks; any-of guards do not.
- The default (`phase: "beforeHandle"`, `match: "all"`) is unchanged, so existing apps that authenticate in `beforeHandle` keep working.

### `requireRoles()` options [#require-roles-options]

`requireRoles()` authorizes by role, group, or permission instead of OAuth scope. It reads a list-valued claim from `ctx.state.user.claims` (what `jwk()` stamps), or from `ctx.state.user` itself when an auth helper stamped a plain object (`basicAuth()`, or `bearerAuth()` whose `validate` returned one). No caller is a `401` with `WWW-Authenticate: Bearer`; a caller without the roles is a `403` that does not name them.

```ts
import { jwk, requireRoles } from "@daloyjs/core";

app.use(jwk({ jwks, algorithms: ["RS256"], issuer, audience }));

requireRoles(["Books.Admin"]);                                   // Entra app roles (`roles`)
requireRoles(["admins"], { claim: "cognito:groups" });           // a named top-level claim
requireRoles(["delete:books"], { claim: "permissions" });        // Auth0 RBAC
requireRoles(["editor", "admin"], {                              // Keycloak, any one role
  claim: (c) => (c.realm_access as { roles?: unknown } | undefined)?.roles,
  match: "any",
});
```

- A string `claim` is one top-level claim name, read verbatim, so names containing dots or colons work. `__proto__`, `constructor`, and `prototype` are refused at construction, and only the claims object's own properties are read.
- The claim value may be an array of strings or a space-delimited string. Anything else, a missing claim, or a reader that throws counts as no roles (fail closed).
- The check always runs in `preBody`, before the body is read and before `idempotency()` or `responseCache()` could replay a stored response, so there is no `phase` option. Register the authentication hook first.

### `BearerAuthOptions` [#bearer-auth-options]

Since 1.12.0, `validate` may return a user-shaped object instead of `true`. It is stamped on `ctx.state.user`, so `requireScopes()` (reading `scopes`) and `requireRoles()` work with any verifier: a provider SDK, an introspection call, or a test stub. Return `{ sub, scopes, claims }` to match `jwk()`. See [pattern B on the auth overview](/docs/auth#pattern-bearer).

`bearerAuth()` and `jwk()` pass any token value through verbatim, with no length, charset or prefix check, so new token formats keep working. The one exception is a token containing whitespace or a comma. Duplicate `Authorization` headers are comma-joined into one value (`Bearer a, Bearer b`), so such a token is a `401` and never reaches `validate()` or the JWT verifier.

## Composition primitives

```ts
every(...layers: Hooks[]): Hooks      // run every lifecycle phase in order
some (...layers: Hooks[]): Hooks      // pass the first successful preBody/beforeHandle auth gate
except(when: ExceptPredicate, hooks: Hooks): Hooks  // exempt paths from preBody + beforeHandle gates

type ExceptPredicate =
  | string                            // path glob: "*" = one segment, "**" = any suffix
  | string[]                          // any-of globs
  | ((ctx) => boolean | Promise<boolean>);

// Globs match the canonical path the router dispatches on. The Node adapter
// resolves raw %2e%2e dot segments and folds \ to / before routing, and the
// Node and Lambda adapters refuse (400) a Host containing \ / ? # @ % or
// whitespace, so a crafted target cannot slip past an except() glob. Route
// params and wildcards never bind "." or "..".
```

## Connection info & proxy posture [#connection-info-and-proxy-posture]

```ts
type ForwardedHeaderSource = "x-forwarded-for" | "forwarded" | "cf-connecting-ip"; // since 1.16.0
type BehindProxyConfig =
  | "none"
  | "loopback"
  | { hops: number; header?: ForwardedHeaderSource }
  | { cidrs: readonly string[]; header?: ForwardedHeaderSource };
interface ConnInfo { remoteAddress?: string; remotePort?: number; tls?: boolean }

getConnInfo(req: Request): ConnInfo | undefined;
setConnInfo(req: Request, info: ConnInfo): void;   // adapter helper
assertBehindProxy(cfg: BehindProxyConfig | undefined): void;
resolveClientIp(ctx, cfg?: BehindProxyConfig): string | undefined;
readRemoteAddress(ctx): string | undefined;
readRemotePort(ctx): number | undefined;
pickForwardedForByHops(header: string, hops: number): string | undefined;
parseForwardedHeader(header: string | null): string[];          // RFC 7239 for= values, in order
readForwardedClientIp(req, source: ForwardedHeaderSource, hops: number): string | undefined;

// Spoof-resistant client IP: reads `hops` entries from the RIGHT of
// X-Forwarded-For (the slots your own proxy chain wrote). Falls back to
// X-Real-IP only when hops === 1; past that a chain shorter than the
// declaration yields undefined rather than a caller-settable header.
resolveForwardedClientIp(req: Request, hops?: number, trustedPeers?, source?: ForwardedHeaderSource): string | undefined;
```

### Which header carries the client address [#forwarded-header-source]

`X-Forwarded-For` is the default. Since 1.16.0 the object forms of `behindProxy` take a `header` so the same hop and peer rules read a different header:

- `"forwarded"`: the RFC 7239 `Forwarded` header. Only `for=` parameters are read, one per comma-separated hop, right to left like `X-Forwarded-For`. Quoted values, bracketed IPv6, `:port` suffixes, and the RFC's `unknown` / `_obfuscated` identifiers are handled; the latter two still occupy their hop (so a proxy writing `for=unknown` can never let the attacker-controlled left entry slide into the trusted slot) but yield no address. There is no `X-Real-IP` fallback for this source.
- `"cf-connecting-ip"`: Cloudflare's single-value header naming the visitor Cloudflare saw. It is one hop by definition, so it works with `{ hops: 1 }` or `{ cidrs: [<Cloudflare ranges>] }` and `{ hops: 2, header: "cf-connecting-ip" }` is refused at construction. Prefer it to `X-Forwarded-For` behind Cloudflare, where a client can pre-populate the latter.

```ts
// Behind Cloudflare, only when the socket peer is a Cloudflare edge:
const app = new App({
  behindProxy: { cidrs: CLOUDFLARE_IPV4_AND_IPV6_RANGES, header: "cf-connecting-ip" },
});

// Behind an RFC 7239 proxy (Traefik, Caddy with `forwarded`):
const app = new App({ behindProxy: { hops: 1, header: "forwarded" } });
```

Every client-identity guard (`rateLimit()`, `autoBan()`, `ipRestriction()`, `geoBlock()`, …) that does not declare its own trust inherits the App posture, header included.
